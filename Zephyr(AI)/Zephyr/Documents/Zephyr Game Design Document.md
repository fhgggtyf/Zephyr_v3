## 1. 产品定义

### 1.1 一句话定位

Zephyr 是一款以高反馈横版战斗为核心的单人动作 Roguelike：玩家在一次次短而高风险的探索中使用两把武器、学习敌人攻击、承受潜能损失，并把本局收益带回 MetaHub，逐步扩大下一局的选择空间。

### 1.2 玩家承诺

玩家每次进入游戏都应该能得到四种明确感受：

1. **操作有重量。** 移动、跳跃、攻击、受击和镜头移动有清楚的起停、前摇、命中反馈和恢复窗口。
2. **风险可读。** 敌人的侦测、预警、攻击窗口和潜能惩罚必须在真正造成损失前给玩家理解和反应时间。
3. **选择有代价。** 武器替换、升级路线、资源消耗、是否继续深入和是否放弃本局都应形成实际取舍。
4. **失败仍然推进。** 倒地会削弱本局潜能，但真正死亡后仍保留局外货币、图鉴、目标和故事进度。

### 1.3 核心支柱

| 支柱 | 设计含义 |
| --- | --- |
| 精确横版动作 | 玩家通过地面、空中、闪避和受击状态管理位置与节奏，而不是依靠自动瞄准或数值碾压。 |
| 双武器表达 | 两个武器槽位提供明显不同的攻击节奏、范围、资源消耗和风险。左键直接使用 Primary，右键直接使用 Secondary，玩家通过当下按哪一个攻击键做战术选择。 |
| Potential | HP 归零先进入 Down；连续倒地会侵蚀特定 Potential，降低玩家未来强化收益。 |
| 手工空间、种子选择 | 房间布局和战斗空间由设计师制作，局内通过种子选择房间、敌人集合和波次组合，而不是生成不可控的地图。 |
| 可学习的敌人 | 普通敌人共享一套可读的 Patrol、Alert、Chase、Telegraph、Attack 循环；Boss 用时间线组合复杂攻击。 |
| 局内构筑、局外成长 | 一局内强调即时取舍；局外通过货币、武器图鉴、机制解锁和潜能预算扩大长期选择。 |

### 1.4 非目标

- 不做多人、联机、PVP 或合作模式。
- 本阶段不做程序化地图布局生成；只做手工房间的种子驱动选择。
- 不做背包和深层库存管理。玩家始终只持有两把武器。
- 不使用 DOTS/ECS。目标同屏规模适合 MonoBehaviour 方案。
- 不把复杂玩法逻辑写进 Animator Controller 或场景脚本事件中；动画表现服从状态和攻击时间线。

**当前实现（简述）：** Unity URP + New Input System + ScriptableObject 数据驱动框架已建立；内容完整度仍低于本 GDD 的最终目标。

## 2. 目标玩家与体验节奏

### 2.1 目标玩家

Zephyr 面向喜欢以下体验的玩家：

- 愿意通过重复尝试学习敌人前摇和空间位置。
- 喜欢短时间内做出武器、路线和风险判断。
- 能接受失败，但希望失败产生可理解的长期进展。
- 在动作精度和构筑选择之间都能找到乐趣。

### 2.2 一局的节奏

一局不是连续无差别战斗，而是由以下节奏交替组成：

1. **进入房间：** 观察地形、门、镜头边界、可交互物和敌人出现位置。
2. **遭遇建立：** 敌人巡逻或待机，玩家决定靠近、绕后、换武器或先处理高威胁目标。
3. **战斗爆发：** Telegraph 给出窗口，玩家在地面和空中管理攻击、闪避、资源和位置。
4. **清理与回收：** 波次结束，拾取货币或武器，确认生命、资源和 Potential 风险。
5. **路线选择：** 选择下一个房间类型，决定奖励、风险和进度。
6. **阶段结算：** 通过 Boss 或阶段出口，进入下一阶段或结束本局。

### 2.3 单次操作的反馈链

所有高频动作应尽量形成：

`输入 → 状态变化 → 动画/位移 → 命中或资源事件 → 音效/数字/镜头 → 可读的下一窗口`

任何一个环节缺失都会让玩家感觉输入没有生效。尤其是攻击、受击、空中攻击被拒绝、资源不足、倒地和镜头边界，必须有可观察反馈。

## 3. 玩家角色与移动

### 3.1 移动能力

玩家是标准 2D 横版角色，基础移动能力包括：

- 左右移动与转向。
- 地面跳跃。
- 空中二段跳（由机制解锁控制）。
- 冲刺（Dash）与翻滚（Roll），由机制解锁或配置控制；消耗 Energy。
- 蹲下、蹲走。
- 受击僵直、击飞、起身。
- 攻击期间的武器特定移动。

玩家的移动不是“速度直接写入位置”。水平移动、跳跃和击飞都要尊重 Rigidbody2D、地面检测、碰撞和状态优先级。

### 3.2 状态与优先级

角色状态由统一状态机驱动。常规状态包括 Idle、Walk、Sprint、Crouch、JumpStart、JumpMid、JumpEnd、Dash、Roll、PrimaryAttack、SecondaryAttack、Knockback、Hitback、Getup。

状态设计原则：

- Death 和不可打断的 Hitback 优先级最高。
- Hurt/Knockback 能中断普通攻击，但无敌状态下的命中不产生新的受击。
- Attack 的结束由攻击数据、动画或攻击控制器确认，不由输入松开决定。
- 空中攻击必须同时满足“处于空中”和“本次输入所指定槽位的武器具有空中攻击能力”。
- 机制未解锁时，相关输入可以被读取，但状态转换必须被条件拒绝。

### 3.3 攻击移动

攻击移动支持两类表达：

1. **固定攻击移动：** 攻击阶段使用作者指定的速度，适合需要固定距离和确定落点的招式。
2. **输入驱动攻击移动：** 攻击阶段读取当前移动输入，并根据作者指定的速度曲线或当前移动方式调整速度，适合玩家在攻击中修正位置的武器。

二者都必须保证攻击判定、动画时序和碰撞结果稳定；移动输入不能绕过攻击的有效窗口，也不能让攻击状态因为玩家持续按方向而无法结束。

### 3.4 资源与移动

玩家有 Stamina 与 Energy 两条资源：

| 资源 | 主要用途 | 回复规则 |
| --- | --- | --- |
| Stamina | 配置为耐力消耗的武器攻击、跳跃、二段跳、持续奔跑（Sprint） | 停止消耗满 1 秒后按固定速率回复；持续奔跑会不断重置延迟。 |
| Energy | 配置为能量消耗的武器攻击、冲刺（Dash）、翻滚（Roll），以及未来的技能、蓄力和特殊动作 | 与 Stamina 独立计时，停止消耗满 1 秒后回复。 |

资源不足时，动作不能进入会消耗资源的状态。失败的消耗尝试不应重置回复计时器。

**当前实现（简述）：** Player prefab 已有移动、地面检测、资源控制、攻击状态、空中攻击条件和受击状态；不同攻击移动数据由武器组件承载。

## 4. 战斗设计

### 4.1 战斗目标

战斗的关键不是单纯提高每秒伤害，而是让玩家在有限空间内同时处理：

- 敌人的攻击距离和方向。
- Telegraph 反应窗口。
- 自己的攻击前摇、有效帧和恢复。
- 两把武器的节奏和资源。
- 地面与空中位置。
- 受击累积、击飞上限与无敌时间。
- 当前房间剩余敌人和下一波压力。

### 4.2 伤害类型

基础伤害类型只有：

- **AD：** 物理攻击，受 Armor 和物理穿透影响。
- **AP：** 法术攻击，受 Magic Resist 和法术穿透影响。
- **True：** 真实伤害，不受 Armor/MR 影响。

元素是附加标签，不是第四类伤害。火、冰、雷、风、土等元素通过 Buff/异常系统产生燃烧、冻结、感电等状态效果。

### 4.3 伤害解析顺序

一次命中按以下顺序处理：

1. 暴击。
2. 背刺。
3. 不同类别的额外乘区相乘。
4. 普通攻击伤害方差。
5. Armor/MR 与穿透减伤。
6. Shield 分摊与破盾溢出。
7. 生成伤害结果、命中事件、数字和击杀归属。

百分比最大生命伤害在攻击生成时折算进统一伤害值；它针对目标最大生命值，不依赖攻击者的某个隐藏 ScalingStat。

### 4.4 防御与穿透

- 固定穿透对目标防御做减法。
- 百分比穿透按比例削减防御，再应用固定穿透。
- 物理攻击使用 Armor，法术攻击使用 Magic Resist。
- 设计上保留有效防御空间，避免目标防御过低导致所有伤害差异被抹平。

### 4.5 暴击、背刺与乘区

- 暴击率与暴击倍率是两个独立的选择。
- 当暴击率为 0 时，爆伤没有直接收益；先建立暴击机会再提高爆伤。
- 背刺仅适用于敌人，依赖敌人当前朝向。
- M1、M2、M3 是三个独立乘区，分别对应武器类型增伤，武器稀有度增伤，以及元素伤害增伤；同一乘区内的增量相加，不同乘区互相相乘。
- 乘区设计用于制造构筑差异，不应成为所有武器都必须追求的单一答案。

### 4.6 Shield

Shield 是独立于 HP 的防御层。武器通过 ShieldCoeff 决定对护盾的处理方式：

- 低于 1 的系数允许部分伤害穿透。
- 大于等于 1 的系数可以专门处理破盾或高护盾目标。
- Shield 不参与 Armor/MR 计算，先减伤再进行护盾分摊。

普通武器不应默认拥有高破盾系数。护盾是用来制造武器选择和敌人类型差异的附加层，而不是每个木桩都必须存在的基础血条。

### 4.7 攻击时序

每一步攻击至少要定义：

- Windup：前摇与可躲避窗口。
- Active：命中判定窗口。
- Recovery：后摇和被反击风险。
- CancelWindow：允许进入下一连段的输入窗口。
- DamageMultiplier：该段攻击倍率。
- 是否 Finished。

命中判定应与动画有效帧对齐。Hitbox 的位置、尺寸、朝向和显示选项属于可编辑数据或组件，设计师可以在 Scene/Prefab 中直接看见和调整。

### 4.8 受击、击退与击飞

普通受击时间由伤害和 Tenacity 决定：

`knockbackDuration = damage / 100 × (1 - TenacityReduction)`

设计规则：

- 同一次受击期间，更短的新受击不能覆盖剩余时间；更长的可以刷新。
- 普通受击累计预计超过 0.8 秒时进入 Hitback。
- Hitback 期间玩家沿曲线飞行、无敌，并在撞到墙或顶时反弹。
- 落地后进入一秒 Getup，仍然无敌并闪烁。
- Knockback、Hitback、Getup 都是可挂动画的正式状态。
- 每次有效受击都可以触发镜头震动；无敌命中不震动。

**当前实现（简述）：** 统一 DamageCalculator、HealthComponent、武器伤害构建、资源消耗、受击三状态、伤害镜头震动和 Enemy/Boss 命中组件已落地；复杂远程武器接线和完整 Buff 内容仍需补齐。

## 5. 武器设计

### 5.1 双武器结构

玩家始终拥有 Primary 与 Secondary 两个武器槽位。两个槽位不是“当前武器/备用武器”关系，而是两个可随时直接调用的攻击来源：

- 左键 PrimaryAttack 永远请求 Primary 武器。
- 右键 SecondaryAttack 永远请求 Secondary 武器。
- 两个输入分别检查对应武器的资源、空中攻击组件、连段和攻击数据。
- 玩家不需要先切换 Active 武器，才能使用另一把武器。

系统仍可保留一个 `ActiveSlot`/高亮槽位，但它的唯一设计语义是 **Replacement Target**：告诉玩家下一次拾取武器会替换 Primary 还是 Secondary。它不决定攻击输入使用哪把武器，也不应被描述为“当前战斗武器”。如果代码继续使用 `ActiveSlot` 这个旧名称，UI 和设计文档必须把它解释为“待替换槽位”。

没有背包、备用仓库或拾取后的第三层选择界面。玩家在拾取前先把 Replacement Target 指向想覆盖的槽位；武器拾取是有意图的交互，避免磁吸误替换。

### 5.2 武器的个性来源

每把武器至少应通过以下三项形成个性：

1. **攻击节奏：** 连段长度、前后摇、终结段、取消窗口。
2. **空间表达：** Hitbox 形状、方向、垂直范围、攻击移动。
3. **构筑关系：** 伤害类型、暴击、背刺、元素、穿透、护盾系数、资源消耗。

可选差异包括远程投射物、重力、穿透数量、元素异常、特殊移动和独立乘区。

### 5.3 组件化数据

武器由 WeaponSO 和可组合的 ComponentData 描述。可用组件包括：

- HitBox：几何、偏移、朝向和可视化。
- AttackDirection：攻击方向约束。
- AttackFacing：转身策略。
- AttackMovement：固定速度或输入驱动移动。
- AirAttack：允许该武器在空中进入攻击状态。

“能否空中攻击”不是玩家全局能力，而是本次 Primary/Secondary 输入对应武器的能力。某一槽位的武器不能空中攻击时，只拒绝该槽位的攻击请求；另一槽位仍按自己的组件独立判断。

### 5.4 武器稀有度与词条

武器稀有度决定词条数量和数值范围。武器固有数据不通过 Potential 缩放；角色在本局取得的身体属性增益才受 Potential 影响。

设计方向：

- 普通武器保证规则清晰。
- 高稀有度武器允许更复杂的元素、穿透、护盾和特殊窗口。
- 词条应改变决策，不只是把所有数字加大。
- 房间、商店和 Boss 奖励提供不同稀有度预期。

### 5.5 连段

连段是每把武器自己的固有序列。连续按同一槽位的攻击键，在指定取消窗口内预输入下一段；太久没有输入则回到第一段。改按另一槽位会改用另一把武器，不需要修改 Replacement Target，也不能把另一槽位误当成同一武器的下一连段。

连段的设计目的不是强制玩家打完整套，而是让玩家根据敌人状态选择停在安全段、冒险换取终结段，或改按另一槽位直接切换攻击来源。改用另一槽位时，另一把武器按自己的连段规则处理，不把两把武器串成一个连段。

### 5.6 远程武器

远程攻击共享同一 DamageInfo 管线，但通过池化 Projectile 产生命中。投射物数据包括速度、重力、生命周期、穿透数、发射偏移和伤害类型。

### 5.7 武器内容生产标准

每把正式武器在进入游戏前应有：

- 至少一张可替换 Icon 与完整攻击动画。
- 地面攻击和空中攻击的明确设计判断。
- 每段攻击的有效帧截图或 Gizmo 检查。
- 资源消耗与收益理由。
- 对普通敌人、护盾敌人和 Boss 的适用场景。
- 最少一条“缺点”，防止武器只在所有维度都更强。

**当前实现（简述）：** WeaponSO、WeaponRuntime、双槽 WeaponController、组件生成器、武器编辑器、动画事件命中和空中攻击组件已存在；稀有度词条生成、商店内容和远程完整接线属于后续内容阶段。

## 6. 玩家属性、Potential 与风险

### 6.1 十项核心属性

以下十项属性拥有 Potential：

| 属性 | 用途 |
| --- | --- |
| Attack | 物理攻击基础值 |
| MagicAttack | 法术攻击基础值 |
| Armor | 玩家物理防御 |
| MagicResist | 玩家法术防御 |
| MaxHp | 最大生命 |
| Stamina | 耐力上限 |
| Luck | 伤害方差偏移、掉落和商店质量 |
| Tenacity | 受击时间缩短 |
| Energy | 能量上限 |
| AttackSpeed | 攻击频率 |

### 6.2 不携带 Potential 的 Meta 属性

暴击率、暴击倍率、穿透、最大护盾、ShieldCoeff 增益、移动速度、拾取范围、方差减少、伤害减免、Potential 预算等属于 Meta/永久属性，不参与十项 Potential 缩放。

### 6.3 四层属性模型

同一核心属性由四层相加：

1. Base：永久角色基础值和局外升级。
2. RunGains：本局取得、受 Potential 缩放的增益。
3. Modifiers：本局的非 Potential 状态和房间效果。
4. TempModifiers：短时药剂、Buff 或限时效果。

只有 RunGains 使用：

`实际增益 = 原始增益 × 当前属性 Potential / PotentialMax`

这样可以让玩家在一局中获得“这件奖励很强，但我当前该属性的 Potential 不适合它”的判断，而不是所有奖励都无条件等价。

### 6.4 Potential 的局内生命周期

- 每局开始时，系统将预算中的 **N−M 点随机分配**到十项属性，构成本局的随机基底——每局起点潜能分布不同，是动态难度的来源。
- 随后剩余的 **M 点由玩家自行分配**，M 不得超过 N（M ≤ N）。
- Potential 上限为10。
- Down 只削减本局 Potential，不会跨局保留损失。
- 真死亡后重新开始下一局时，不携带上局的 Potential 数值。

### 6.5 Down、Respawn 与 True Death

HP 降至 0 时：

1. 玩家停止作为敌人的有效目标。
2. 播放死亡动画。
3. 根据最后有效伤害来源寻找 PotentialAttack 和 TargetPotential。
4. 扣除：`PotentialAttack × 2^DownCount`。
5. DownCount 增加1。
6. 若目标 Potential 仍大于0，显示死亡 UI 并允许 Respawn。
7. 若任意 Potential 小于等于0，进入 True Death，Respawn 灰掉，只能 Give Up。

每个正式敌人都应携带 PotentialAttack。值为0只用于测试，表示本次倒地不造成潜能损失；不存在平均分摊到所有属性的默认分支。

### 6.6 死亡 UI

死亡界面必须让玩家一眼看到：

- “You died”及中文翻译。
- 哪个 Potential 被扣了多少，例如 `Health: 10 - 1`，旧值白色，损失红色。
- Respawn 和 Give Up 两个按钮。
- Potential 归零时 Respawn 灰掉且不可点击。

死亡展示不暂停游戏时间，但玩家和敌人逻辑应已进入死亡流程，敌人将玩家视为离开侦测范围并继续巡逻。

**当前实现（简述）：** StatsCore、PlayerStatsInitializer、PotentialAttackSource、PlayerDeathController、DeathView、DownCount 和 Respawn/True Death 分支已建立；完整潜能分配、MetaHub购买界面和所有奖励内容仍需作者资产。

## 7. 普通敌人与 Boss

### 7.1 普通敌人的战斗职责

普通敌人不是玩家武器的简化版。它们拥有自己的 EnemySO、EnemyStats 和内置攻击，不依赖 WeaponSO、玩家槽位或玩家组件。

普通敌人应通过少量清晰行为产生组合压力：

- 近战贴身与封位。
- 远距离预警和投射物。
- 高韧性或高生命的空间占用。
- 针对某一 Potential 的倒地惩罚。

### 7.2 普通敌人状态循环

默认循环为：

`Patrol → Alert → Chase → Telegraph → Attack → Cooldown/Chase`

被命中时优先进入 Hurt；HP 归零时优先进入 Death。

设计规则：

- Facing 玩家且进入 AggroRange 时快速进入交战。
- 背向玩家但进入 DetectionRange 时先 Alert，停下、转身，再交战。
- Telegraph 默认不能转向，给玩家明确的侧移和绕后窗口。
- 只有显式挂载 TelegraphTurn 组件的敌人才能在预警期间转向。
- Attack 必须是可重复循环，不能一次攻击后永久停在攻击状态。
- AttackDefinition 自己拥有总时长、冷却、有效窗口和伤害倍率。
- Hitbox 组件负责形状和显示；Gizmo 在编辑时显示，攻击生效时变为危险颜色。

### 7.3 敌人动画

每个正式敌人应有 Animator。状态进入时由 StateAction 设置动画参数，动画负责表现，状态机负责逻辑。

基础敌人至少需要：Idle、Patrol、Alert、Chase、Telegraph、Attack、Hurt、Death。攻击动画的时长应与 AttackDefinition 的总时长一致；有效帧和 Hitbox 时间窗应能通过编辑器核对。

### 7.4 Boss 设计目标

Boss 不是把普通敌人的数字放大，而是一个可读的攻击编排者。Boss 的攻击应该让玩家识别：

- Boss 处在什么阶段。
- 当前攻击针对近距离还是同高度远距离。
- 哪些部分是真正伤害窗口。
- 攻击后有多长时间可以接近或恢复资源。

### 7.5 教程 Boss （原型宙斯）

Boss 拥有两阶段：HP 低于50%进入第二阶段。第二阶段在每个主要攻击后追加环绕左右的斩击，并将攻击间隔缩短至1.5秒。

攻击集合：

1. **远距离水平冲刺：** 冲刺本身有伤害。
2. **高跳、投矛、冲向矛：** 先跳起，在地面放置有伤害的矛，再冲向矛；矛和冲刺是独立伤害段。
3. **近距离竖斩接横斩：** 两段独立伤害窗口。
4. **近距离地面插矛：** 以 Boss 为中心向左右约2单位产生伤害。
5. **第二阶段环绕斩：** 每次主要攻击后向左右约3单位产生伤害。

在攻击间隔内，Boss 只朝玩家接近，不发起新的攻击。每个攻击可以拥有任意数量的 HitboxSegment，每个段独立配置时间、尺寸、偏移、目标层和是否每目标仅命中一次。

### 7.6 敌人内容生产标准

每个敌人资产必须写清：

- 它想迫使玩家做什么动作。
- 玩家最安全的反应窗口。
- 失败时造成的 HP 和 Potential 后果。
- 它与同房间其他敌人的组合关系。
- 它的攻击是否允许绕后、跳过或利用地形规避。

**当前实现（简述）：** BasicEnemy 使用统一状态机；EnemySO、EnemyStats、EnemyBrain、EnemyMotor、EnemyAttackController、MeleeHitbox 和 TelegraphTurn 已建立。Boss 使用独立的 BossController 时间线，基础原型攻击和第二阶段已实现；敌人阵容、波次选择和完整动画内容仍待制作。

## 8. 房间、阶段与空间进度

### 8.1 手工房间原则

房间是设计师明确制作的战斗空间，不是随机拼接的平台。房间负责：

- 平台、墙、地面、危险区域和可通行路线。
- 出入口、镜头外框、CameraZone 和固定装饰。
- SpawnPoint 的位置与标签。
- 房间类型、奖励类型和是否清门。

房间不直接写死“这一波生成哪只敌人”。敌人由当前阶段的 ActiveSet 和 SpawnPoint 标签共同决定。

### 8.2 房间类型

- Combat：标准多波战斗。
- Elite：更高压力和更高价值。
- Shop：用本局货币购买武器或刷新选择。
- Treasure：偏奖励、偏探索。
- Rest：恢复或准备。
- Event：叙事、特殊规则或非战斗选择。
- Boss：Boss 战与阶段奖励。

### 8.3 波次设计

波次数量和每波敌人数量由 Spawner 根据 RoomType、当前阶段、房间深度、波次序号和种子计算。作者只配置 SpawnPoint 的位置和标签。

波次规则：

- 当前波敌人全部死亡后才进入下一波。
- 波次之间有明确但不必然安全的间隔。
- 选中的 SpawnPoint 应有约0.35秒的生成预警。
- 一个 SpawnPoint 可以在不同波次再次使用。
- 房间所有波次完成后解锁门并发出 OnRoomCleared。

设计目标是持续压力，而不是每清一波就完全安全。预警必须足够让玩家反应，但不能让玩家把下一波当成免费休息。

### 8.4 阶段与敌人集合

每个阶段有若干个 stage-locked EnemySet。一次运行在阶段开始时用种子选定其中一个集合；该集合决定：

- 本阶段可出现的敌人。
- 主题背景和环境音。
- 敌人统计和威胁组合。

同一个 EnemySet 不跨阶段复用。阶段难度主要通过不同的作者化集合、房间深度倍率和挑战模式倍率推进，而不是把一个基础敌人无限乘大。

### 8.5 门、出口与路线

房间出口映射到 RoomSlot，而不是直接映射某个具体场景。这样同一个手工房间可在不同运行种子中连接到不同的下一房间。

门有两种交互：

- 走入已解锁门的触发区域。
- 按统一 Interact 键与最近的有效门交互。

门锁、梯子、武器拾取共用同一个交互输入；PlayerInteractor 通过距离选择最近的有效目标。

**当前实现（简述）：** RoomController、房间 Scene 分类、SceneSO、相机边界和若干基础房间场景已建立；动态波次、RoomSelector、EnemySet 资产和完整房间内容仍属于内容制作阶段。

## 9. Run、存档与局外循环

### 9.1 单次 Run 的结构

一局从 LoadingRun 创建 RunData 开始，包含：

- 种子。
- 当前 HP、Stamina、Energy。
- 本局 Potential 和 DownCount。
- 当前两把武器与连段状态。
- 本局 Buff。
- 本局货币。
- 当前阶段、深度、房间、访问记录和波次状态。
- 本局待提交的 Objective。

RunData 只服务当前局，真正死亡或胜利后结算并清除。

### 9.2 MetaData

MetaData 跨局保留：

- 永久货币。
- 基础属性升级。
- Potential 预算 N 与可分配份额 M 的升级。
- 暴击与双穿等战斗 Meta 升级。
- 额外乘区解锁。
- 武器图鉴。
- 机制解锁。
- 已完成 Objective、已触发 Story Beat。
- 设置与语言。

局内不能直接修改 MetaData。局内完成的目标先写入 RunData.PendingObjectives，只有结算时才提交到 MetaData。

### 9.3 存档槽

主菜单提供最多三个独立存档槽：

- 第一次打开游戏时三个槽都为空。
- Continue 仅在存在有效存档时可用。
- Start Game 在有空槽时允许选择新建槽。
- 槽位已满时，先要求删除一个槽，再创建新槽。
- 删除需要通用确认弹窗，并且按钮文本和状态必须清晰可见。

存档至少保存 MetaData 和可选的 RunData。中断存档用于恢复正在进行的房间、装备、Buff、波次和资源状态。奖励随机使用种子和上下文计算，使读档不会改变同一状态下的奖励结果。

### 9.4 结算

True Death 或胜利时：

1. 把本局货币转为永久货币。
2. 提交新武器图鉴记录。
3. 提交 PendingObjectives。
4. 写入 MetaData。
5. 清除 RunData。
6. 进入 MetaHub。

普通 Down 不触发结算，也不离开 InRun。

### 9.5 主菜单与启动路径

正常启动顺序为：Initializer → Persistent → MainMenu。Persistent 在整个会话中不卸载，负责场景加载、事件、存档、音频、本地化、对象池和计时器。进入 Tutorial、MetaHub 或 Run 时再加载 GameManager；回到 MainMenu 时卸载 GameManager。

冷启动 Prefab 只用于把任意场景直接打开进行依赖初始化，不应改变正常 MainMenu → Tutorial/MetaHub/Run 的流程。

**当前实现（简述）：** SaveSystem 三槽 JSON 存档、SceneSO + Persistent SceneLoader、MainMenu、Initializer、Persistent、GameManager 和 ColdStartup 框架已存在；完整 MetaHub 购买界面、RunSelector 和中断恢复的所有内容仍需补齐。

## 10. MetaHub、成长与机制解锁

### 10.1 MetaHub 的功能

MetaHub 是局外空间，不是战斗房间。玩家在这里：

- 查看永久货币。
- 购买基础属性和战斗属性升级。
- 提高下一局 Potential 预算或可分配份额。
- 解锁双跳、冲刺（Dash）、翻滚（Roll）等机制。
- 查看武器图鉴和长期目标。
- 观看排队的故事对话。

MetaHub 的作用是把失败转化为下一局的选择增加，而不是简单把所有敌人变得更容易。

### 10.2 机制解锁

机制解锁与普通数值升级分开：

- 每个机制有成本和前置 Objective。
- 未满足前置条件时显示但不可购买。
- 购买后永久有效，不会因死亡或换槽消失。
- 玩家状态机通过 MechanicUnlockedCondition 判断是否允许进入相关状态。

### 10.3 设计边界

- Potential 不跨局扣除。
- 不允许通过 MetaHub 直接恢复上一局已损失的 Potential。
- 永久升级应增加策略宽度，而不是让某个固定属性成为所有武器的必选项。
- 图鉴奖励保持小幅，不能把首次获得某武器变成永久碾压。

**当前实现（简述）：** MetaUpgradeSO、MetaUpgradeSystem、MechanicUnlockSO/System、RunEndSettlement、Objective 与 StoryBeat 框架已存在；MetaHub 的实际购买和展示内容仍是待填充内容。

## 11. 对话、故事与本地化

### 11.1 故事表达方式

Zephyr 采用线性、无分支的两人对话。故事由 Objective 推动，而不是靠玩家在运行中选择大量对话分支：

`事件完成 → Objective 记录 → 结算提交 → MetaHub 进入时评估 StoryBeat → 依优先级播放对话`

当前底层稿已经锁定了叙事的载体、触发时机和持久化规则，但没有锁死具体世界观、角色关系或主线终点。这部分应由上层内容继续定义；在正式故事资产出现前，不在系统层臆造角色、阵营或历史事件。

### 11.2 对话视觉

- 左侧角色的肖像位于屏幕最左侧上方。
- 右侧角色的肖像位于屏幕最右侧上方。
- 肖像为无边框 160×160，可直接替换 Sprite。
- 当前说话者显示肖像和名字；另一侧可隐藏或降低存在感。
- 对话框位于肖像下方，不让肖像被对话框遮挡。
- 所有文字、角色名和按钮均支持中文与英文。

### 11.3 世界触发对话

场景中放置 DialogueTrigger，玩家进入 Collider 后触发。触发器可以设置：

- 只触发一次。
- 必须完成的 Objective。
- 必须触发的 StoryBeat。
- 最低 Run Stage。
- 是否要求 Tutorial 已完成。

所有条件按 AND 组合。触发器不直接写故事逻辑，只引用 DialogueSO。

### 11.4 输入与时间

对话开始时：

- 关闭 Gameplay Action Map。
- 启用 Dialogue Action Map。
- 清空玩家缓存的移动、跳跃、攻击和闪避输入。
- 由 NextLine 推进文本。
- 对话结束后恢复 Gameplay Action Map。

在 InRun 中出现对话或其他模态 UI 时暂停游戏时间；死亡流程是例外，不暂停时间。MetaHub 对话不需要冻结战斗，因为 MetaHub 本身不运行 InRun 战斗 Tick。

### 11.5 本地化规则

- 所有玩家可见文本必须经过 Unity Localization 或 LocalizationManager。
- 中文和英文表必须同时有 key。
- 文本长度变化不能破坏按钮、HUD 和对话框布局。
- 角色名、统计名、死亡文本、主菜单、存档提示和确认弹窗都不能保留硬编码英文。
- 字体必须有 CJK fallback，避免中文显示方框。

**当前实现（简述）：** DialogueSO、DialogueTrigger、DialogueManager、DialogueView、双 Action Map 和中文/英文表已建立；更多故事资产、完整 MetaHub 故事队列和所有 UI 文本迁移仍需继续。

## 12. UI 与信息层级

### 12.1 统一画布

UI 参考分辨率固定为 960×540。CanvasScaler 使用 Scale With Screen Size，所有重要区域必须在宽屏、窗口缩放和最小支持尺寸下保持可见。

UI 不是装饰性卡片堆叠，而是帮助玩家在动作中快速读取：

- 当前状态。
- 可用资源。
- 武器选择。
- 潜能风险。
- 交互结果。

### 12.2 InRun HUD

HUD 位于 GameManager 的 Gameplay UI 层，只在有玩家时显示：

- 右上角：本局收集的 Coins。
- 左上角：Health、Stamina、Energy 三条横向状态条。
- 左下角：Primary 与 Secondary 两个武器图标并列显示。若显示槽位高亮，它表示“下一次拾取将替换此槽”，不能让玩家误以为只有高亮武器可以攻击。
- 需要时显示交互提示、房间状态和伤害数字。

HUD 的图标、边框、背景和字体都是可替换资源。数值变化应通过事件或组件绑定更新，而不是由每个 UI 元素自行读取并决定游戏逻辑。

### 12.3 主菜单

主菜单第一屏包含：

- Start Game。
- Continue Game。
- Settings。
- Exit Game。

Continue 在无有效存档时灰掉且不可点击。Start Game 根据槽位情况进入新建存档面板；Exit Game 使用通用确认弹窗，弹窗只负责显示和回传 Yes/No，具体文本由调用方通过本地化配置提供。

### 12.4 Death UI

死亡 UI 独立于 HUD，使用可编辑 Prefab，详见 6.6。死亡界面不应依赖运行时生成 Image 来承载主要视觉。

### 12.5 UI 交互原则

- 按钮本身只触发中央控制器方法，不持有存档、场景或游戏流程逻辑。
- 图标按钮优先使用熟悉图标，陌生图标提供 tooltip。
- 不在界面中堆叠互相嵌套的卡片。
- 不让文字溢出按钮、状态条或弹窗。
- 颜色必须同时通过形状、位置或文字表达状态，避免只依赖颜色。

**当前实现（简述）：** MainMenu、存档面板、确认弹窗、Gameplay HUD、武器图标、DeathView 与对话 Prefab 已存在；通用 Panel Stack、完整 Stats Panel、浮动文本池和 MetaHub UI 仍待实现或完善。

## 13. 镜头与空间阅读

### 13.1 Hollow Knight 风格的跟随

镜头由场景中的 CameraController 所有，不放在每个房间里重复实现。镜头不是每帧紧贴玩家，而是使用 Deadzone：

- 玩家在 Deadzone 内时镜头保持稳定。
- 玩家离开 Deadzone 时镜头重新追上。
- 水平方向和垂直方向都使用 Deadzone。
- 进入新房间、重生或重要预警点时允许 Snap。

这能减少横版平台跳跃中的持续漂移，并让房间构图更稳定。

### 13.2 软边界

每个房间提供外层 WorldBounds。镜头在边缘平滑夹住，不渲染房间外部，但不把玩家硬锁在视口中心。房间可大于当前屏幕，边界是镜头约束而非玩家碰撞墙。

### 13.3 CameraZone

场景可以放置多个 CameraZone，对局部区域自定义：

- FollowOffset：例如 Boss 房间让玩家处于画面下方。
- SoftBounds：窄走廊或竞技场的局部范围。
- DeadzoneMultiplier：更稳定或更灵敏。
- Priority：重叠区域时决定谁生效。

玩家离开区域后应重新评估其他仍激活的区域，而不是瞬间退回房间默认镜头。

### 13.4 镜头震动

镜头震动必须叠加在已经计算好的逻辑镜头位置上。震动偏移不能反过来成为下一帧的跟随输入，否则会造成边界漂移和镜头越跟越偏。震动来源包括有效受击、Boss 重击和重要环境事件。

**当前实现（简述）：** CameraBounds、CameraZone 和 Deadzone 风格 CameraController 已建立；震动逻辑已有独立视觉偏移修正，仍需在实际房间和不同分辨率下持续调参。

## 14. 音频与表现反馈

### 14.1 音频层级

音频分为 SFX、Music、UI 三条总线。每条总线可独立音量和静音。

### 14.2 事件驱动

战斗代码不直接决定播放哪个声音；事件层负责连接：

- 命中、暴击、背刺、元素异常。
- 敌人死亡与玩家 Down。
- 房间清理与进入新房间。
- Primary/Secondary 攻击、Replacement Target 改变、拾取和交互。
- GameFlow 状态改变。

### 14.3 关键反馈

- 普通命中与暴击必须能被听出差异。
- Telegraph 需要有与危险等级相称的提示音。
- Down、True Death、Respawn、Give Up 有清晰的状态声。
- Boss 阶段转换需要音乐、音效或空间表现上的升级。
- 高频声音使用池化 AudioSource，避免每次命中创建对象。

**当前实现（简述）：** AudioManager 与事件方向已建立，完整 AudioEventSO 资产和音乐内容仍待制作。

## 15. 输入与可读性

### 15.1 Action Map

核心输入分为：

- GamePlay：Move、Sprint、Roll、Jump、Crouch、PrimaryAttack、SecondaryAttack、Interact。
- Dialogue：NextLine。
- UI/MetaHub：计划中的菜单、暂停和局外交互输入。

输入动作表达意图，角色状态决定当前意图是否可执行。对话是唯一由 DialogueManager 负责切换的专用 Action Map。

### 15.2 输入设计

- PrimaryAttack 直接解释为 Primary 武器攻击；默认鼠标左键。
- SecondaryAttack 直接解释为 Secondary 武器攻击；默认鼠标右键。
- 两个攻击输入在地面和空中都分别检查自己槽位的武器组件；不存在先选择 Active 武器再攻击的步骤。
- Replacement Target/旧名 ActiveSlot 只决定拾取会覆盖哪个槽位，与攻击路由无关。
- Interact 统一处理门、梯子和武器拾取。
- 输入缓冲用于提升跳跃和攻击的容错，但不能绕过资源和状态条件。
- UI 必须支持键盘/手柄焦点顺序，不能只依赖鼠标。

### 15.3 可读性目标

- 关键前摇有明确动作、颜色、声音或粒子至少两种信号。
- 状态条数字和颜色同时存在。
- 不把不可执行输入默默吞掉；资源不足、武器不能空袭、按钮禁用都应有可理解状态。

## 16. 数值与平衡原则

### 16.1 目标曲线

设计稿的总体目标是让正常构筑的伤害曲线有层次：早期为两位数，中期进入低三位数，后期约600，极佳组合可接近低四位数；同时不让所有敌人都因为数值膨胀而变成一刀秒。

### 16.2 木桩参考

用于理论验证的标准木桩为：

| 档位 | HP | Armor/MR |
| --- | ---: | ---: |
| R1 | 150 | 50 |
| R2 | 225 | 65 |
| R3 | 360 | 80 |

最近的低配初始配置为：50 Attack、1.0 AttackSpeed、0% Crit、1.5x CritDMG、0 FlatPen、0% Pen、M1/M2/M3 = 1.0。

在原升级增量的二分之一时，P70 参考结果约为：

| 档位 | P70 DPS | 连续 TTK |
| --- | ---: | ---: |
| R1 | 35.00 | 4.286s |
| R2 | 41.89 | 5.371s |
| R3 | 53.35 | 6.747s |

这组数据不是最终战斗平衡，而是提醒设计者：如果敌人 HP/防御增长很快，攻击成长即使“每项看起来合理”，整体 TTK 仍会持续恶化。

### 16.3 边际收益原则

- 评估属性时使用 `TTKbefore / TTKafter - 1`，并同时查看实际秒数变化。
- 低配时攻速、固定穿透和最大生命伤害通常更容易显出价值。
- 暴击伤害必须和暴击率一起观察。
- 百分比穿透必须在高防御目标上测试；已有固定穿透时其收益会明显下降。
- 最大生命伤害必须在低、中、高 HP 目标上分别测试。
- AOE 收益只能作为横版上半圆参考；地面和空中密度分开记录，不能把它当作保证收益。
- 任何单个极端组合都必须和 P70/P90 及路径权重一起看，不能只看 Max。

### 16.4 平衡护栏

- 不让单一属性在所有防御、生命和资源场景都严格支配其他属性。
- 不让固定穿透在低防御目标上直接清空防御并失去其他武器价值。
- 不让百分比最大生命伤害在 Boss 和普通敌人上共享同一无上限收益。
- 不用纯增加敌人 HP 解决所有后期难度；空间、波次、组合和攻击覆盖同样重要。
- 每个新属性必须有“在哪些目标或构筑中不值得选”的反例。

## 17. 内容制作规范

### 17.1 数据资产

所有可调数值优先放进 ScriptableObject 或 Prefab：

- 武器、连段、Hitbox、攻击移动和资源消耗。
- 敌人属性、侦测、巡逻、攻击、PotentialAttack 和掉落。
- Boss 阶段、攻击时间线和 Hitbox 段。
- 房间、SpawnPoint、出口、CameraZone 和奖励。
- Meta 升级、机制解锁、Objective、StoryBeat 和 Dialogue。

### 17.2 场景职责

| 场景 | 设计职责 |
| --- | --- |
| Initializer | 只负责冷启动 Persistent。 |
| Persistent | 全局事件、存档、场景加载、音频、本地化、对象池、计时。 |
| MainMenu | 存档槽、开始/继续、设置、退出。 |
| GameManager | 当前游戏阶段的 UI、相机、战斗和投射物服务。 |
| Tutorial | 一次性的固定教学流程，不创建 RunData。 |
| MetaHub | 局外货币、升级、机制和故事。 |
| LoadingRun | 创建或恢复 RunData，准备首个房间。 |
| Room_Generic/Room_Boss | 单个可卸载房间和其空间内容。 |

### 17.3 编辑器验收

新内容提交前必须在编辑器检查：

- Prefab 根节点完整且可正常导入。
- Sprite、Animator、Collider、Layer 和 Sorting Layer 正确。
- Hitbox Gizmo 与实际命中范围一致。
- SceneSO 引用真实场景，不依赖手写路径。
- Localization key 在中英文表都有值。
- 状态机 Transition 没有丢失条件或重复状态。
- 所有池化对象有正确回收路径。

### 17.4 资产可替换性

主要视觉必须来自 Prefab 或 SO 引用，尤其是：

- 主菜单背景。
- 对话框、肖像、按钮、继续指示器。
- 死亡界面。
- 武器图标和 HUD。
- Boss 矛、攻击特效和命中反馈。

运行时代码只负责绑定状态和文字，不把作者之后要替换的主要视觉画死。

## 18. 完成定义与开发优先级

### 18.1 Vertical Slice 完成定义

一个可交付的最小完整切片需要包含：

1. 冷启动后稳定进入 MainMenu。
2. 新建、继续、删除三槽存档可用，首次启动槽位为空。
3. 从 Tutorial 进入 MetaHub，再进入一间 InRun 房间。
4. 玩家能移动、跳跃、闪避，并能用左键 Primary、右键 Secondary 分别攻击和消耗对应资源。
5. 至少一把地面武器和一把空中武器。
6. 一个普通敌人完整循环并可重复攻击。
7. 一个带两阶段的 Boss，所有攻击窗口可读。
8. 玩家 Down、Potential 扣除、Respawn、True Death 和结算可走通。
9. HUD、死亡 UI、对话 UI 和中英文切换可用。
10. 房间边界、CameraZone、镜头震动和重生 Snap 不互相污染。

### 18.2 后续开发顺序

**第一优先级：可玩的闭环**

- 完成主菜单到一局 Run 的流程。
- 固定玩家、基础敌人、一个房间和一个 Boss 的动画/碰撞验收。
- 完成死亡和结算，不允许存档损坏或状态卡死。

**第二优先级：内容扩展**

- 增加武器差异、敌人集合、房间类型和 Boss 攻击。
- 增加掉落、商店、MetaHub 购买与机制解锁。
- 补齐 Objective、StoryBeat 和可重复触发的对话内容。

**第三优先级：打磨与规模**

- 统一音频事件、浮动数字、VFX、屏幕反馈。
- 进行高密度房间、Boss 和投射物的性能测试。
- 完善中英文排版、手柄焦点、设置和可访问性。

## 19. 设计决策记录

以下决定视为当前设计基线，修改时需要同时更新数值分析和内容规范：

1. 两个武器槽，不做背包。
2. 武器拾取按 Interact，不磁吸；货币可磁吸。
3. 左键固定请求 Primary，右键固定请求 Secondary；ActiveSlot 只表示下一次拾取的 Replacement Target，不控制攻击。
4. 空中攻击是每个槽位武器自己的能力，不是全局默认能力。
5. 普通敌人不用 WeaponSO；Boss 可用独立时间线控制复杂攻击。
6. HP 归零先 Down；Potential 归零才 True Death。
7. 每个正式敌人有 PotentialAttack，0 只用于测试，不平均分摊。
8. Potential 只在局内侵蚀，不跨局保留损失。
9. 房间布局手工制作，种子只选择房间、敌人集合和波次安排。
10. Tutorial 是一次性固定流程，不是 RoomSO，也不创建 RunData。
11. 所有普通场景加载请求经过 Persistent 的 SceneLoader。
12. 对话使用左右无框 160×160 肖像，并切换到 Dialogue Action Map。
13. InRun 模态 UI 暂停游戏时间，死亡流程不暂停。
14. 镜头使用 Deadzone + 软边界 + 场景 CameraZone，震动不能污染跟随锚点。
15. 中文和英文是首发支持语言，所有 UI 与故事文本必须本地化。
