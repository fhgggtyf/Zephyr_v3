# Zephyr 当前实现架构独立复评报告

> 复评日期：2026-10-12  
> 项目根目录：`D:\GitHub\Zephyr_v3\Zephyr(AI)\Zephyr`  
> 复评目标：只评价 architecture correctness、模块边界、耦合程度和代码架构整洁度；不评价玩法质量、美术质量、数值平衡、内容丰富度或性能。

## 1. 结论

本次复评完全从当前仓库实现重新开始，不继承之前阶段的分数，也不因为某项工作曾经完成就自动加分。

**当前整体架构评分：8.7 / 10。**

**结论：当前不能诚实地评为 9.0 以上，但已经达到可以继续普通功能开发的高质量架构门槛。**

这不是对前序拆分工作的否定。与最初审查相比，项目已经从“逻辑上分组、编译上大 Core/Assembly-CSharp 混合”的状态，进入了有明确程序集依赖、有 Contracts/Runtime 分层、有场景生命周期边界、有架构自动门禁的状态。

本次没有发现以下结构性问题：

- 旧 `Zephyr.Core` 仍作为其他程序集的直接依赖枢纽；当前 policy 中旧 Core 已无程序集消费者。
- 程序集循环依赖。
- 新增平行 StateMachine、SceneLoader、EventBus、战斗服务或全局 Manager。
- 运行时普通业务通过 `Resources.Load`、`GameObject.Find` 或全局 Tag 查找进行资源/对象定位。
- 架构测试、基础 EditMode 测试或 Vertical Slice PlayMode 测试当前不可复现。

仍然存在、并且足以阻止 9.0+ 的问题是：

1. 运行时代码仍有 **91 个**受控的具体单例、场景扫描和场景加载调用，其中 **80 个是 Singleton 读取**。
2. `Zephyr.Player` 有 15 个程序集引用，`Zephyr.Gameplay.Interaction` 和 `Zephyr.Core.Dialogue` 各有 8 个引用，部分高层模块仍然是高扇出枢纽。
3. 场景扫描虽然已经被门禁登记并局部收窄，但 `GridAligner`、`SceneStatsModifierController`、`DialogueManager`、`MainMenuView` 等仍承担运行时发现职责；其中有些是基础设施合理边界，有些仍可以进一步改成显式上下文或序列化引用。
4. 若干核心类继续混合生命周期协调、服务访问、状态推进和具体业务策略，尤其是 Flow、Save/Meta、Camera、Player interaction/UI 相关实现。
5. 大量类型仍默认为 `public`，模块内部 API 收窄程度不足。当前统计到非 Editor、非测试运行时程序集约 510 个类型声明，其中约 405 个为显式 `public` 类型、3 个为显式 `internal` 类型，说明编译边界已经建立，但类型可见性边界尚未完全收紧。

因此，当前最准确的评价是：**架构边界已经可用且受到自动检查保护，但运行时依赖收窄和内部 API 清理尚未完成。**

### 2.1 9.0+ 的硬门槛

为了避免“测试有了所以架构就是 9 分”的误判，本项目使用以下额外门槛：

1. 模块边界、生命周期和 Contracts 三项不得低于 9.0。
2. 不存在程序集循环依赖，且旧兼容宿主不再作为领域公共依赖中心。
3. 普通业务不得新增具体 Singleton、全局场景扫描、直接场景加载或运行时路径资源查找。
4. 现有 Singleton/SceneScan/SceneLoad 债务必须有 owner、风险、替代边界、预算和删除条件；同时债务总量应在持续下降，而不是只被登记。
5. 高扇出模块必须有明确的组合根职责，不能把具体实现类型继续向领域模块扩散。
6. 架构测试、EditMode、关键 PlayMode 链路和 Console 状态必须有当前可复现证据。

当前第 1、2、3、6 项已基本满足；第 4、5 项仍有实质性缺口，所以本轮不能给 9.0+。

## 4. 依赖图和耦合证据

### 4.1 当前程序集结构

当前解析到 **30 个 asmdef**，架构测试检测不到循环依赖。关键依赖方向如下：

```text
Core.Contracts
    ↓
Core.Runtime
    ↓
Core.Combat

Core.Persistence ─────┐
Core.Meta ─────────────┤
Core.Localization ─────┤
Core.UI ───────────────┤
                       ↓
Core.Flow / Scene Lifecycle

StateMachine ─────────────→ Player / Enemies
Combat + Contracts ────────→ Player / Enemies / Weapons / Items / Projectiles
Flow + Contracts ──────────→ Rooms / Interaction / Player
```

当前没有 `Zephyr.Core` 的程序集消费者，说明此前的 Core Split 已经达到一个真实的编译边界，而不是只有命名空间迁移。

### 4.2 高耦合模块

按程序集引用数量观察：

| 程序集 | 项目程序集引用数 | 判断 |
| --- | ---: | --- |
| `Zephyr.Player` | 15 | 最高。是当前最需要继续拆分的领域枢纽。 |
| `Zephyr.Gameplay.Interaction` | 8 | 交互入口知道过多服务和 UI/Meta 细节。 |
| `Zephyr.Core.Dialogue` | 8 | Dialogue 同时承担 UI、输入、Meta 和存档协作。 |
| `Zephyr.Core.Flow` | 6 | 组合根合理，但需要避免向普通业务下沉。 |
| `Zephyr.Tests.PlayMode` | 16 | 测试专用，不作为生产耦合扣分。 |

高引用数量本身不是错误，但必须能解释为组合根、适配器或测试边界。当前 Player、Interaction、Dialogue 中仍有部分引用是具体服务消费，而不是稳定 Contract 消费，因此需要继续收窄。

## 5. 全局状态与隐式访问

架构门禁当前记录：

| 规则 | 调用点组数 | 实际调用数 | 说明 |
| --- | ---: | ---: | --- |
| Singleton | 55 | 80 | 主要涉及 EventBus、SaveSystem、GameFlow、StoryProgressionService、SceneLoader、DialogueManager 等。 |
| SceneScan | 7 | 7 | 主要涉及 Camera、SceneStats、Dialogue/EventSystem、Grid 对象发现。 |
| SceneLoad | 4 | 4 | Initializer、ColdStartup、SceneLoader 的受控加载/卸载入口。 |
| **合计** | **66** | **91** | 全部有 owner、风险、替代边界、预算和删除条件。 |

这 91 个调用不应全部被当作同等严重：

- `Initializer`、`PersistentBootstrap`、`GameManagerBootstrap`、`SceneLoader` 的少量实例解析属于组合根或基础生命周期边界，合理性较高。
- `GameFlow` 与 SceneLoader 协作属于流程基础设施，但应避免具体 Singleton 读取扩散到业务 Controller。
- `DialogueTrigger`、`PlayerInputReader`、`PlayerInteraction`、`MainMenuController`、`TutorialController`、`MetaHubController`、`RoomController` 等组件中的直接读取，属于应继续迁移的业务级依赖。
- `CameraController`、`SceneStatsModifierController`、`DialogueManager`、`MainMenuView`、`GridAligner` 的场景扫描有部分基础设施合理性，但仍应区分“寻找场景结构”与“寻找业务服务”；后者应改为显式引用或 context。

因此，当前门禁质量很高，但当前架构洁净度不能按门禁数量替代。门禁把债务变成可见、可控、不可增长；它没有把 91 个调用自动变成理想设计。

## 6. 数据与 Contracts 边界

当前表现较好：

- `Core.Contracts` 无项目依赖，包含稳定接口和值类型。
- Combat 实现已依赖 Contracts/Runtime，不再把伤害、武器枚举和状态类型藏在旧 Core 宿主中。
- Save DTO、RunData、MetaData 已从大 Core 中收窄到 Persistence。
- 掉落使用稳定 ID 和 pickup contract，避免 Enemies 直接依赖具体 WeaponSO。
- SO 主要承担共享配置；前序迁移已经明确把运行时状态放回 Actor/Runtime 对象。

仍需继续注意：

- Contracts 当前有较多 `public` 类型，内部协议和真正跨程序集 API 尚未完全区分。
- 部分接口命名同时承担生命周期、服务访问和领域行为，可能继续形成“万能 Gateway”。
- `Core.Flow` 对 Meta/Persistence/UI 的组合责任仍较宽，未来应优先增加窄接口，而不是把更多类型塞进现有 gateway。

## 7. 代码职责与整洁度

### 优点

- `SceneLoader` 是统一场景 authority，普通业务没有新增平行加载路径。
- StateMachine 基础设施保持独立，Player/Enemy 通过上层 Action/Condition 扩展。
- Enemies、Items、Weapons 的迁移桥已经被清理，掉落通过 contract 和 room gateway 传递。
- Save/Meta、UI/Localization、Audio/Camera、SceneScan 等历史风险都已有独立边界和测试记录。
- 现有架构门禁能从编译结果和 IL 读取实际调用，而不是只依赖手写字符串检查。

### 扣分点

- `Player` 仍然是大模块，包含输入、状态机、移动、战斗、死亡、生成、交互和表现多个变化轴。
- `GameFlow`、`SaveSystem`、`CameraController`、`DialogueManager` 和部分 Interaction 类仍兼具编排与服务定位职责。
- 类型可见性偏宽，许多本应是程序集内部实现的类型仍然是 `public`，导致未来依赖更容易扩散。
- 业务组件虽然不再使用无门禁的全局查找，但仍有较多具体 Singleton 读取，测试能阻止增长，却不能替代显式注入。
- 场景扫描和反射兼容逻辑集中在少数大类中，后续修改这些类的风险仍高于普通领域类。

## 9. 最终评分判断

### 能否达到 9.0 以上？

**以当前实现重新独立评分：不能。当前为 8.7/10。**

如果只看程序集拆分和验证体系，局部可以达到 9.0 以上；如果把整个游戏当前 implementation 作为一个整体，并把运行时服务访问、职责集中度和 API 暴露面纳入评价，整体还没有达到 9.0+。

### 进入 9.0+ 的最小修复集合

1. 将业务级直接 Singleton 读取从 `DialogueTrigger`、`PlayerInputReader`、`PlayerInteraction`、`MainMenuController`、`TutorialController`、`MetaHubController`、`RoomController` 等组件迁移到组合根提供的 Gateway/Context，优先减少 80 个 Singleton 调用中的业务部分。
2. 把剩余业务级场景扫描改成序列化引用、场景 context 或明确的 owner API；保留真正属于基础设施的场景结构扫描，但必须把用途写入 policy。
3. 收窄 `Zephyr.Player`：至少分离 Player Flow/Spawn、Player Interaction、Player Presentation 与 Player Combat adapter 的依赖面，不必重新拆基础 StateMachine。
4. 对 `GameFlow`、`SaveSystem`、`CameraController`、`DialogueManager` 做职责收窄，把文件 IO、场景解析、反射兼容、视图构造和业务策略拆成内部协作者。
5. 把 Contracts 和领域程序集内部实现的可见性从 `public` 逐步收窄为 `internal`，只保留跨程序集真正需要的 API。
6. 让架构门禁增加“业务 Singleton 数量下降”和“高扇出程序集预算”检查，避免后续只登记债务而不减少债务。

完成以上集合后，再以相同权重和硬门槛复评；如果测试与 PlayMode 证据保持可复现，合理目标是 **9.1-9.3**，而不是仅靠继续增加 asmdef 数量获得分数。

## 10. 最终结论

Zephyr 当前已经是**可持续开发、边界可审查、依赖不会无声恶化**的架构，而不是需要推倒重来的架构。前序拆分的价值已经落地到编译边界、Contracts、场景生命周期和自动化门禁中。

但“架构有门禁”与“架构已经干净”是两个不同维度。当前的 8.7 分准确反映了这一点：结构基础和验证能力接近优秀，业务侧具体服务访问、Player/Dialogue/Interaction 高耦合和内部 API 过宽仍阻止整体达到 9.0+。

本轮复评不建议继续横向增加程序集数量。下一步应集中于**服务访问收窄、业务场景扫描清除、Player/Dialogue 职责拆分和 API 可见性治理**，并以现有架构门禁作为不可回归的验收标准。
